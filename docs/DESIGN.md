# 设计与维护

## 为什么先做一个小种子

首版验证的是可追溯的数据结构、稳定 ID、真实可运行 API，以及 API/离线数据一致性。它不是中国食材全集。先确保少量样本准确、有来源且可以再分发，再持续扩充，比一次性生成未经核验的大表更有价值。

## 版本与兼容性

- `/v1` 是 API 主版本。删除或改变已公开字段/语义需要主版本方案。
- `schemaVersion` 是数据结构版本，当前 `1.0.0`。
- `datasetVersion` 是内容快照版本，当前初始种子 `0.1.0`。新增/校正条目均应发新快照。
- ID 不包含名称、分类或上游 ID。名称、分类甚至来源改变时，只要所指食材相同，ID 不变。
- 同物改名保留原名为有依据的别名。不同食材合并/拆分时应先增加 deprecated/replacedBy 等显式迁移结构，不静默回收 ID。
- 未记录过敏原、营养、学名、加工状态或原产地，不能根据分类代为推导。

## 别名与检索

仅进行 NFKC、去首尾空白、casefold，不做自动繁简转换、拼音、分词、拼写纠错或语义推断。繁简与地区名必须明确收录。

同一食材内规范名/别名规范化后不能重复；不同食材可能有同名别名。这不是唯一键，查询会返回所有匹配项，不能直接用于无歧义配料解析。地区歧义、切法、加工形态、上下位类目需要人工建模。

## 来源与权利

每条 sourceRef 声明字段级支持范围，来源备注说明核验方法。存在来源链接不代表自动验证了页面的全部事实。分类、稳定 ID 和条目选择为项目编辑判断。

代码 MIT，数据 CC0；第三方来源自身许可独立保留。任何许可不明的数据只可作为待审核研究材料，不进入公开数据。未来图标单独设计、存储与许可，不能沿用数据许可覆盖任意图片。

## 一致性、导出与缓存

应用启动时加载且验证三个源 JSON，保留字节快照。HTTP JSON 导出和离线脚本使用相同字节；查询返回其中原记录。CSV 的数组与 null 通过 JSON 编码保留类型。SHA-256 涵盖三个源文件，来源许可或分类变化同样改变快照哈希。

API 固定快照不自动热更新，避免并发请求看到半次编辑。ETag 对实际响应体计算，支持 HEAD 和 If-None-Match 条件请求。服务不在请求期间访问上游站点。

## 扩展路径

1. 增加有来源的条目、繁简/地区别名和数据变更审查。
2. 根据真实菜谱需求设计粒度：物种、可食用部位、加工方式和规格，避免“鸡肉=鸡胸肉”等误合并。
3. 调味品进入前先定义与食材的交叉规则，扩展 kind/schema，并新增测试；目前校验器拒绝其他 kind。
4. 原创图标需要稳定资源 ID、格式/尺寸、作者与独立许可证。当前 `icon` 固定为 null，改变其结构需发布 schema。
5. 用实际流量决定数据库/搜索引擎；当前线性扫描适合小种子，性能未做生产压测。
6. 生产环境采用受维护的 WSGI/ASGI 或其他生产 HTTP 框架，实现部署、限流、观测和安全测试，而不是把此开发服务器直接暴露到公网。
